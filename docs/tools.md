## File search, plans and loops

- `find` and `grep` search the working directory. They use fff (`@ff-labs/fff-node`, an indexed finder) and fall back to ripgrep when fff cannot load or returns an error, or when `grep` is called with `exact: true`. Each result says which backend answered in `details.backend`. If neither fff nor `rg` works, the tools return a named error (`search_unavailable`). A ripgrep run that fails, for example on an invalid glob, returns `search_rg_failed` with its first error line instead of an empty result. The fff databases live in `${PIROBOROS_HOME}/fff/`. Results under protected locations (`PIROBOROS_HOME`, `~/.ssh`, `.env` files, `guard.deny`) are dropped, credential-shaped text is redacted, and output is capped at 20,000 characters.
- The `plan` tool keeps a short task list for the current request. The model sends the whole list each time, with exactly one item in progress. The list is shown to the model with every message of that request and is cleared when the next user message starts. Set `"planning": false` in `settings.json` to remove the tool; the change applies at the next start.
- If the model makes the same tool call five times in a row, it gets a reminder to change approach. If the same call fails eight times in a row, the turn ends and the status line says `stopped (stuck)`. Denied calls do not count. If the model's run produces no output and no tool is running for ten minutes, the turn ends and the status line says `stopped (idle)`. If one run makes 256 tool rounds without finishing, the turn ends and the status line says `stopped (round limit)`.
- A `bash` command is refused when its text names a protected location (`PIROBOROS_HOME`, `~/.pi`, `~/.ssh`, `~/.claude`, `guard.deny`) in a Windows, Git Bash, WSL or `~`/`$HOME`/`%USERPROFILE%` spelling, names a credential file (`auth.json`, `.netrc`, `id_ed25519` and the like, but not `*.pub`), or uses `..` to climb out of the `guard.allow` folder it runs in. A path inside a `guard.allow` folder is not refused. This is a tripwire against accidents, not confinement: bash is not sandboxed and a command can be worded around it.

## Shell confinement

With Workspaces on (the default), Vesperia's `bash` commands run inside bubblewrap on Linux when `bwrap` is on PATH and a self-test passes at the moment the Workspace opens. The choice is kept for that Workspace and made again when it is reopened. On Ubuntu install the `bubblewrap` package. Ubuntu 23.10 and later restrict unprivileged user namespaces by default; when that blocks bubblewrap the self-test fails and the start notice names the reason. On Windows the commands run inside bubblewrap in WSL (see below). macOS has no backend yet, so its commands are not confined, and the notice and `/conclave status` say so.

- What a command sees: the whole system read-only, the Workspace read-write, an empty `/tmp`, and a home folder with nothing in it. `PIROBOROS_HOME`, `~/.pi`, `~/.ssh`, `~/.claude` and every `guard.deny` folder outside the home are hidden. Folders named on PATH under your home (`~/bin`, `~/.local/bin`, a Node version folder) stay visible read-only, so tools installed there keep working. The live `.git/objects` of the project is visible read-only so that git works in the Workspace.
- What it cannot do: write outside the Workspace (the write fails, or lands in `/tmp` or the empty home folder and disappears when the command ends) or read your credentials. A live project inside your home is hidden; one outside your home, its `node_modules` included, is still readable by absolute path. Because `/tmp` and the home folder are fresh for every command, `git commit` there uses only the `user.name` and `user.email` kept from the live repository's local config.
- Network: `workspace.network` (default `true`) lets installs work. With it on, a command can reach your network and send any file it can see. Set it to `false` to cut the network.
- A command is passed to `bash -c` as one argument, so it can be at most 131,071 bytes and cannot hold a NUL byte; a longer one is refused with a message that suggests a script file in the Workspace. A command that runs past the timeout is killed with everything it started.
- If a command cannot start, it fails with an error and is never run again without confinement. If bubblewrap was not usable when the Workspace opened, the start notice, her brief and `/conclave status` say the shell is not confined. `workspace.confine: "none"` turns confinement off on purpose.

### The seccomp filter

Every sandbox, native or in WSL, also loads a small seccomp filter (written in `src/ws/confine.ts`, no library). It does three things: `socket` and `socketpair` calls for the AF_VSOCK family fail with EAFNOSUPPORT, the three `io_uring` calls fail with EPERM, and a process using a CPU architecture other than x86_64 or aarch64, or the 32-bit x32 system calls, is killed. Everything else is allowed. AF_VSOCK is not scoped to the sandbox's network namespace, and in WSL the Windows host answers on it (one of its ports serves your drives), so closing it matters more than the network setting. The self-test checks that a vsock socket cannot be created; a filter that does not load or a failing self-test gives no sandbox, with the warning, never an unfiltered one.

Residuals: with the network on, a command can still reach TCP ports on the Windows host and on your network, and can send any file it can see. 32-bit programs (x86 or ARM) and x32 programs do not run in the sandbox. The filter is not a general system call policy.

### Windows: bubblewrap in WSL

Install WSL 2 with a distribution whose default user is not root (Ubuntu 24.04 is the tested one), then in that distribution install `bubblewrap`, and Node 26.5 or later if your project needs `npm`. Do not use the `docker-desktop` distribution; it cannot run commands. Set `workspace.wsl.distro` to pick a distribution other than the default; the distribution and user are fixed when a Workspace opens and kept while they still resolve.

- Commands run as that user through `wsl.exe` with an argument list, never a shell string, with a minimal environment (PATH, HOME, USER, LANG and a few terminal settings) built inside WSL: nothing from your Windows environment reaches them.
- The Workspace stays on your Windows drive and the sandbox sees it through `/mnt/<drive>`. Everything else Windows-backed is hidden: your profile, `System32`, `PIROBOROS_HOME` and every `guard.deny` folder. A Windows program inside the Workspace does not run, and the WSL interop socket is masked.
- `node_modules` lives in a folder in the distribution's own filesystem (under `~/.local/state/piroboros-ws`), so `npm ci` is fast; it is empty on the Windows side and is removed with the Workspace. Files a command writes there are not merged.
- The Workspace folder is on drvfs, which is slow for many small files: expect the first `git status` in a project of 5,000 tracked files to take most of a minute and later ones a couple of seconds. The start notice gives an estimate above 1,000 files. A path inside the Workspace that the sandbox shows as `/mnt/c/...` is the Linux view of a Windows path; the file tools want the Windows form.
- `workspace.network: true` gives the commands the WSL VM's network, which includes the Windows host. Set it to `false` to cut it.
- A project on a network share (UNC path) is not confined, with the reason in the notice.

## Skills

A skill is a folder with a `SKILL.md` file. The file starts with a block between two `---` lines that holds a `name` and a `description`, and the instructions follow. Skills are for the main chat. The Conclave members, the compactor and Vesperia do not get them.

- **Where they come from.** In this order, and the first skill with a name wins: `PIROBOROS_HOME/skills`, then the `skills` folder inside `.agents` in your user profile, then the project folders, which are the `skills` folder inside `.agents` and the one inside `.piroboros` in the working directory. A skill is a folder one level down, `<folder>/<skill>/SKILL.md`. A link to a folder is followed. A folder with no `SKILL.md` of its own is listed as skipped and is not searched further.
- **What is read.** Only `name` and `description`, as plain, quoted or block (`>` and `|`) values. Other keys, including nested ones, are ignored. A name is lowercase letters, digits and single hyphens, at most 64 characters, and it may differ from its folder name. A description is cut to 512 characters, and a `SKILL.md` over 256 KB is skipped. A bad file is skipped with a reason that `/skills` shows, and it never stops startup.
- **What the model sees.** One line per skill (name, description and folder) in a `skills` section of the system prompt, after the chat section. The text changes only when the list changes, or when a name, description or folder does, so prompt caching keeps working. It is capped at 20 KB, filled in the order above, and `/skills` lists what did not fit. The model opens a `SKILL.md` with the `read` tool when a task matches it, and the section says that a `SKILL.md` at a listed path is your instruction. With no skills installed there is no section. A skill deleted after the last scan gives a read error until `/reload`.
- **Project skills need a yes.** The first time a project skill is seen, and again whenever its `SKILL.md` changes, the chat asks one question for all of them, listing the names and paths. Yes loads them. No records each as declined, and it stays out until its file changes; typing `/name` for it says so. The answers are in `PIROBOROS_HOME/skills-trust.json`, which is checked like the other config files: an edit outside piroboros is shown at startup, and a missing, corrupt or edited file means every project skill is asked about again. The question opens when the chat screen opens. Until you answer, the index holds your own skills only, and a yes adds the project ones. With `--print` no question is possible, so project skills are left out, nothing is recorded and one line on stderr says how many. Only `SKILL.md` is pinned. Scripts and other files beside it can change without a new question, so say yes only to a folder you trust.
- **Learned skills.** With `learning.model` set, piroboros can propose skills from your chat. They are staged outside the skills folder and written to `PIROBOROS_HOME/skills` only by `/learn accept <name>`; see [Chat commands](configuration.md#chat-commands).
- **Commands.** `/skill-name some request` is sent to the chat exactly as typed, and the model reads the skill. Skills appear in the command list after the built-in commands, with their descriptions. A skill named like a built-in command, such as `conclave`, stays available to the model only, and so does a name that starts with a digit. A name with a digit in it is a command only when it is a loaded skill, so `/42 is the answer` and `/v2` stay ordinary text. `/skills` lists the loaded, shadowed, skipped, declined, waiting and over-budget skills. `/reload` rescans and asks about new project skills.
- **Reading inside `PIROBOROS_HOME`.** The `read` tool may open files under `PIROBOROS_HOME/skills`, so skills installed there work. Files named like secrets stay refused there: `.env` files, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.kdbx`, `id_rsa*`, `id_ed25519*`, `id_ecdsa*`, `*.sqlite*`, `auth.json`, `.netrc` and `.npmrc`. Everything else in the home stays refused for every tool: credentials, settings, the chat database, memory, traces, undo copies and the trust file. Writing under `skills` is refused too, a link out of that folder to a protected place is refused, and a `SKILL.md` that is linked into a protected place is skipped. `find` and `grep` search the working directory only, so they never reach it. The guard is a tripwire for the file tools. It cannot tell a hard link from a file, and shell commands are not confined.
