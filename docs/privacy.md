# Privacy and limits

[Back to the README](../README.md)

- Each provider you configure receives the prompts for the model you assign to it: the main model gets the chat view, the compactor gets the text it summarizes, and each Conclave member gets its own conversation. Everything sent to the compactor is scrubbed first: credential-shaped strings (keys, authorization headers, PEM blocks, JSON and environment-style labels, password phrases), every value in `auth.json`, and the value of every environment variable named `*_API_KEY`, `*_TOKEN` or `*_SECRET` that is 8 or more characters long. Your local log keeps the raw text. A compactor is a third party when its provider is not the one your main model or any Conclave member uses and its address is not loopback; sending the chat to a third party needs your explicit consent (`compactor.allowThirdParty: true`), and a third party also loses hex strings of 32 or more characters. Without consent the compactor shows as disabled with the reason and nothing is sent. This is checked again on every compactor request, so withdrawing consent and running `/reload` stops the next request. "Loopback" means the host is exactly `localhost`, is inside 127.0.0.0/8, or is `::1`, with no user name or password in the URL; piroboros treats it as user-declared local and cannot check that the address really is.
- The learning loop (off until `learning.model` is set) sends slices of the root chat to `learning.model`: your messages, the assistant's replies, tool calls and results cut to 1,500 characters each, the skills index, the text of up to two skills it created that the slice read, the names of its pending and rejected proposals and its own memories. It uses the compactor's scrub and the same consent rule: a provider no other role uses, at a non-loopback address, is a third party and needs `learning.allowThirdParty: true`, which is checked on every request. It reads only chat written after it became permitted, and again from the chat end whenever consent is withdrawn and given back, so withdrawn chat is never sent later. It never sends a Conclave member's own conversation. Staged skills, the ledger and its history are files under `PIROBOROS_HOME/learn`. Telemetry records learner requests like the others, without text.
- Shell output beyond 30,000 characters is cut to its first 12,000 and last 18,000 characters, with a marker in between. The cut part is not saved to any file, so the model has to run the command again to see it.
- Memory-briefing traces (mnemosia) are written under `PIROBOROS_HOME`. A trace is kept while it is under 90 days old or among the 500 newest, and older ones are deleted at startup. The feedback log, `feedback.jsonl`, is capped at 2 MB; when it passes the cap, the oldest lines are dropped.
- The shell tool is not path-confined by the guard. The guard limits which agents may write. A shell command can reach any path your account can, except Vesperia's commands in a confined Workspace (bubblewrap on Linux or in WSL 2, or Docker), which see a read-only system or a container and no home folder (see [Shell confinement](tools.md#shell-confinement)).
- Shell commands that kill processes (`kill`, `pkill`, `killall`, `taskkill`, `tskill`, `Stop-Process`, `spps`, or `wmic` deleting a process) are refused, because `taskkill /IM node.exe` would also end piroboros. This is a tripwire against accidents, not a sandbox: a command can be worded around it.
- piroboros records model request and task timings to `telemetry.sqlite` under `PIROBOROS_HOME` and sends them nowhere. It records provider and model names, tool names, token counts, cost, durations, stop reasons and error kinds, never message text, tool arguments, tool output or error messages. Records older than 7 days are deleted while piroboros runs. Telemetry is on by default; `"telemetry": false` stops it at the next start, and deleting the file removes what was recorded.
- piroboros sends no provider attribution headers. Requests still carry the User-Agent `pi/<version> (<platform>; node/<v>; <arch>)` set by pi-ai.
- The first start of this version copies `chat.sqlite` to `chat.schema1.sqlite` before upgrading it. The copy holds the whole chat, like `chat.sqlite` itself. Delete it once you no longer need to go back to 0.1.0.
- The memory vault mirrors to a private GitHub repository. Only GitHub remotes are tested.
- Vesperia's Workspace copies are folders of exact copies of your git-visible project files, under `%LOCALAPPDATA%\piroboros-ws` on Windows, `~/Library/Application Support/piroboros-ws` on macOS and `$XDG_STATE_HOME/piroboros-ws` (default `~/.local/state/piroboros-ws`) elsewhere. The snapshots taken before a merge and the merge records are stored in `PIROBOROS_HOME/ws/store.sqlite`, and a snapshot holds the live bytes of each path the merge changes. These files can contain secrets that are already in your project. Secret-named files and git-ignored files are not copied. They stay on your machine; what Vesperia reads from the Workspace goes to her model as any file she reads does.
